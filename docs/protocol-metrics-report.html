吞吐量指标 — 概述

吞吐量衡量每条通信路由上单位时间内的数据量。所有吞吐量均基于每条 ProtocolTraceRecord 的 payloadSize 字段计算，该字段记录了消息载荷在截断之前的 JSON 序列化字节长度。

吞吐量 时间分桶

Trace 记录按固定宽度的 2 秒时间桶进行分组。每个桶累加该窗口内所有匹配 trace 的总字节数。

BUCKET_WIDTH = 2000 ms // 对于每条 trace 记录 t： bucket_ts = floor(t.ts / 2000) × 2000 bucket_bytes[bucket_ts] += t.payloadSize // 转换为速率： bytesPerSec = (bucket_bytes / 2000) × 1000

路由分类

每条 trace 根据其 source 和 target 实体字段分类到对应的路由：

路由 匹配条件 采集内容
Operator ↔ Gateway (source=operator, target=gateway) 或 (source=gateway, target=operator) 控制 UI ↔ Gateway的 RPC 和事件
Agent ↔ LLM (source=agent, target=llm) 或 (source=llm, target=agent) LLM API 流量（生命周期、助手流式响应，通过Gateway中继）
Gateway ↔ Node (source=gateway, target=node) 或 (source=node, target=gateway) 远程节点通信（工具调度、状态查询、配对）

Operator ↔ Gateway 吞吐量

吞吐量 Operator ↔ Gateway

衡量控制 UI（Operator）与Gateway服务器之间的数据量。包括所有 WebSocket RPC 请求/响应以及广播到 Operator 连接的事件。

协议：WebSocket（请求/响应为 WS/RPC，广播为 WS/Event）

Agent ↔ LLM 吞吐量

吞吐量 Agent ↔ LLM

衡量 Agent ↔ LLM 路径上的代理流式事件数据量。包括生命周期 start/end 事件和助手 token 流式事件。与 LLM 提供商的实际通信使用 HTTP/SSE 协议，但这些 trace 捕获的是经过Gateway中继后的事件。

协议：HTTP/SSE（源端）→ WebSocket（中继到 UI）

Gateway ↔ Node 吞吐量

吞吐量 Gateway ↔ Node

衡量Gateway与已连接远程节点之间的数据量。包括分发到节点的工具调用请求及其响应。

协议：WebSocket (WS/RPC)

吞吐量聚合统计

统计量 各路由吞吐量统计

对于每条路由，以下统计量从时间分桶采样中导出：

Peak（峰值） = max(sample.bytesPerSec，所有采样) Avg（均值） = mean(sample.bytesPerSec，所有采样) Total（总量） = sum(sample.rawBytes，所有采样) Count（计数） = 有流量的 2 秒桶的数量

吞吐量图表以 bytesPerSec 为 Y 轴、时间为 X 轴绘制，虚线表示平均值。

延迟指标 — 概述

延迟指标衡量关联事件之间的时间间隔。与吞吐量（按时间分桶）不同，延迟在每个离散事件对产生一个采样（例如每次 LLM 调用产生一个 TTFT 采样）。

持久化机制：延迟采样存储在模块级缓存中，在 trace 缓冲区被淘汰后仍然保留。每条 trace 仅处理一次（通过 trace ID 跟踪），以防止重复扫描滑动缓冲窗口时损坏状态机。用户点击「重置」时清空缓存。

Agent ↔ LLM — 首 Token 延迟 (TTFT)

延迟 TTFT（首 Token 时间）

定义：从代理向 LLM 发送请求到收到第一个响应 token 的时间间隔。在一个 agent 运行中，按每次独立的 LLM 调用分别计量。

调用边界检测

单个 agent 运行（runId）中可能包含多次由工具调用分隔的 LLM 调用。事件模式如下：

lifecycle start ─────────────── 边界 #0 assistant 事件 (LLM 调用 1) ← TTFT = first_assistant.ts - boundary.ts tool start → tool end ──────── 边界 #1 assistant 事件 (LLM 调用 2) ← TTFT = first_assistant.ts - boundary.ts tool start → tool end ──────── 边界 #2 assistant 事件 (LLM 调用 3) ← TTFT = first_assistant.ts - boundary.ts lifecycle end

状态机

// 对于每条 trace（仅处理一次，通过 trace ID 追踪）： IF stream="lifecycle" AND phase="start": → 设置 boundary_ts = t.ts, hasBoundary = true, inBurst = false IF stream="tool" AND phase="end": → 设置 boundary_ts = t.ts, hasBoundary = true, inBurst = false IF stream="assistant" AND NOT inBurst AND hasBoundary: → TTFT = t.ts − boundary_ts → 输出采样，设置 inBurst = true IF stream="lifecycle" AND phase="end"/"complete"/"error": → 删除该运行状态

边界情况

场景处理方式
lifecycle start 已从缓冲区淘汰在首次遇到 tool-end 或 assistant 事件时自动初始化状态；从下一个可用边界开始计算 TTFT
tool-end 已淘汰但 assistant 仍在缓冲区无已知边界 → 该次调用不计算 TTFT（0ms 的结果会被过滤）
多个运行同时活跃按 runId 独立追踪

Agent ↔ LLM — 生成延迟

延迟 生成延迟

定义：每次 LLM 响应的持续时间 — 从第一个 assistant 流式事件到工具调用或生命周期结束前的最后一个 assistant 流式事件。在一个 agent 运行中按每次 LLM 调用分别计量。

生成延迟 = last_assistant_event.ts − first_assistant_event.ts （在单次 burst 内，即工具调用或生命周期结束之前）

状态机

// 对于每条 trace（仅处理一次，通过 trace ID 追踪）： IF stream="lifecycle" AND phase="start": → 初始化运行状态（无活跃 burst） IF stream="assistant": → 若无活跃 burst：开始新 burst（burstStart = t.ts, callIndex++） → 延伸 burst：burstLast = t.ts IF stream="tool" OR stream="lifecycle": → 刷新 burst：duration = burstLast − burstStart → 若 duration > 0，输出采样 → 重置 burst 状态 // 进行中的 burst 以 "gen #N (live)" 标签显示，不持久化
实时显示：活跃的（尚未刷新的）burst 会以"(live)"标签包含在统计中。其持续时间随每个新 assistant 事件实时更新。直到工具调用或生命周期结束刷新时才会持久化到缓存。

Gateway ↔ Node 延迟

延迟 Gateway ↔ Node 请求-响应延迟

定义：Gateway与远程节点之间 WebSocket RPC 调用的往返时间。从发送请求到收到匹配响应的时间间隔。

延迟 = response.ts − request.ts // 关联键： key = "${connId}:${reqId}" // reqId 是协议层的请求 ID， // 在同一 WebSocket 连接上的匹配 req 和 res 帧之间共享

匹配算法

FOR EACH trace，其中 (source,target) ∈ {(gateway,node), (node,gateway)} 且 reqId 已定义： IF kind="req": → 存入 inflight 映射：key → { ts, method } IF kind="res": → 在 inflight 映射中查找 key → latency = t.ts − inflight[key].ts → 输出采样，label = 方法名 → 从 inflight 映射中移除 // 超过 60 秒未收到响应的过期条目会被清理
时钟来源：两个时间戳均来自Gateway服务器在 trace 捕获时的 Date.now()。这意味着延迟包含Gateway侧的处理时间，但避免了跨机器时钟偏差问题。

延迟聚合统计

统计量 百分位数与汇总

对于每个延迟指标，以下统计量从累积的采样数组中计算：

sorted = samples.map(s → s.latencyMs).sort(升序) Avg（均值） = round(sum(sorted) / sorted.length) P50（中位数） = sorted[floor(N × 0.50)] P95（95 百分位） = sorted[floor(N × 0.95)] Peak（峰值） = sorted[N − 1] // 最大值 N（样本数） = sorted.length

延迟图表使用散点图（而非折线图），因为延迟采样是事件驱动的，而非按时间分桶。每个点代表一次测量。虚线表示平均值。悬停可查看精确值、标签和时间戳。

持久化与缓冲区管理

层级 缓冲区大小 持久化方式 备注
Gateway环形缓冲区 5,000 条 trace 内存（重启后丢失） 保留完整载荷；服务于 protocol-traces.list 请求
Gateway JSONL 文件 无限制（按天分文件） 磁盘：~/.openclaw/protocol-traces/trace-YYYY-MM-DD.jsonl 完整载荷；可通过导出按钮访问
UI trace 缓冲区 5,000 条 trace 内存（滑动窗口） 由 WebSocket 事件 + 初始加载填充
TTFT 延迟缓存 2,000 个采样 模块级（缓冲区淘汰后仍保留） 通过已处理 trace ID 追踪避免重复处理
生成延迟缓存 2,000 个采样 模块级（缓冲区淘汰后仍保留） 相同机制；进行中的 burst 以 live 标签显示
已处理 ID 集合 最多 8,000 个 ID 模块级 超出限制时清空；最多有少量 trace 被重复处理
