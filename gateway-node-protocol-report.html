1. Overview

The OpenClaw gateway–node protocol is a JSON-over-WebSocket RPC protocol that connects a central gateway (the control plane) with one or more nodes (capability hosts such as iOS/Android devices). The protocol supports bidirectional request–response, server-pushed events, challenge-based device authentication, mobile wake-up via APNS, and a pending work queue for backgrounded nodes.

Architecture

Hub-and-spoke topology. The gateway is the central hub; nodes and operators connect as spokes. All node-to-node communication is mediated by the gateway.

3. Frame Types

All messages exchanged over the WebSocket are JSON objects conforming to one of three frame types.

3.1 Request Frame req

Sent by either side to invoke a method on the peer. Each request carries a unique id used to correlate the response. 

{
  "type": "req",
  "id": "<uuid>",
  "method": "<method.name>",
  "params": { ... }
}
Field Type Description
type "req" Frame discriminator
id string (UUID) Unique request identifier
method string Dot-separated method name
params object Method-specific parameters

3.2 Response Frame res

Returned to the initiator after a request is processed. Matched by id.

Success:

{
  "type": "res",
  "id": "<uuid>",
  "ok": true,
  "payload": { ... }
}

Error:

{
  "type": "res",
  "id": "<uuid>",
  "ok": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "Human-readable description",
    "details": { ... },
    "retryable": true,
    "retryAfterMs": 1000
  }
}
Field Type Description
type "res" Frame discriminator
id string (UUID) Matches the originating request id
ok boolean true for success, false for error
payload object Method-specific result (success only)
error.code string Machine-readable error code
error.message string Human-readable description
error.details object? Optional structured context
error.retryable boolean? Whether the client should retry
error.retryAfterMs number? Suggested retry delay in milliseconds

3.3 Event Frame event

Pushed from the gateway to connected clients. Events are unidirectional and do not expect a response. 

{
  "type": "event",
  "event": "<event.name>",
  "payload": { ... },
  "seq": 123,
  "stateVersion": {
    "presence": 5,
    "health": 10
  }
}
Field Type Description
type "event" Frame discriminator
event string Dot-separated event name
payload object Event-specific data
seq number? Monotonically increasing sequence number
stateVersion object? Per-domain version counters for gap detection

4. Connection Lifecycle

4.1 Handshake Sequence

4.2 Step 1 — Challenge (Gateway → Node)

Immediately after the WebSocket connection opens, the gateway pushes a challenge event:

{
  "type": "event",
  "event": "connect.challenge",
  "payload": {
    "nonce": "random-base64-string",
    "ts": 1737264000000
  }
}
  • nonce: cryptographically random value the node must sign.
  • ts: server timestamp at challenge issuance (milliseconds since epoch).

4.3 Step 2 — Connect Request (Node → Gateway)

The node responds with a connect request containing its identity, declared capabilities, and a cryptographic signature over the challenge nonce: 

{
  "type": "req",
  "id": "<uuid>",
  "method": "connect",
  "params": {
    "minProtocol": 3,
    "maxProtocol": 3,
    "client": {
      "id": "ios-node",
      "version": "1.2.3",
      "platform": "ios",
      "mode": "node"
    },
    "role": "node",
    "caps": ["camera", "canvas", "screen", "location", "voice"],
    "commands": ["camera.snap", "canvas.navigate"],
    "permissions": {
      "camera.capture": true,
      "screen.record": false
    },
    "auth": {
      "token": "previously-issued-device-token"
    },
    "device": {
      "id": "stable-device-fingerprint",
      "publicKey": "base64-encoded-public-key",
      "signature": "base64-signature-over-nonce",
      "signedAt": 1737264000000,
      "nonce": "echoed-nonce"
    }
  }
}
Field Description
minProtocol / maxProtocol Acceptable protocol version range for negotiation
client.platform "ios", "android", "macos", "linux", "windows"
role "node" (capability host) or "operator" (control plane)
caps Array of capability categories the node offers
commands Allowlisted commands the node can execute
permissions Granular permission toggles
device.id Derived from a stable keypair fingerprint
device.signature Signature over the gateway's challenge nonce

4.4 Step 3 — Hello Response (Gateway → Node)

{
  "type": "res",
  "id": "<uuid>",
  "ok": true,
  "payload": {
    "type": "hello-ok",
    "protocol": 3,
    "server": {
      "version": "2026.3.17",
      "connId": "<connection-uuid>"
    },
    "features": {
      "methods": ["node.invoke", "node.pending.pull", "..."],
      "events": ["presence", "health.snapshot", "..."]
    },
    "policy": {
      "maxPayload": 26214400,
      "tickIntervalMs": 30000
    },
    "auth": {
      "deviceToken": "newly-issued-or-refreshed-token",
      "role": "node",
      "scopes": []
    }
  }
}
Field Description
protocol Negotiated protocol version
server.connId Unique connection identifier for this session
features.methods Methods the gateway supports in this session
features.events Events the gateway may emit
policy.maxPayload Enforced max frame size in bytes
policy.tickIntervalMs Expected keepalive interval
auth.deviceToken Token for future reconnections

4.5 Step 4 — Authenticated Session

After hello-ok, the connection enters the authenticated phase. Both sides may send req frames and the gateway may push event frames. The connection remains open indefinitely, with keepalive ticks at tickIntervalMs.

4.6 Step 5 — Disconnection

Either side may close the WebSocket. On close, the gateway:

  1. Removes the node from the NodeRegistry.
  2. Broadcasts a presence event to other connected clients.
  3. Rejects any in-flight invocations with a disconnection error.

5. Authentication & Authorization

5.1 Roles

Role Description Typical Clients

5.2 Operator Scopes

Scope Description
operator.read Read-only access to gateway state
operator.write Write access (send messages, invoke commands)
operator.admin Administrative operations (config, restart)
operator.approvals Approve/deny execution requests

Nodes have no scopes. Their authorization is determined by the caps, commands, and permissions declared at connect time.

6. Node Registry & Session Management

The NodeRegistry class maintains the in-memory store of all live node sessions.

Method Description
register(client, opts) Register a new node connection; maps nodeId → NodeSession
unregister(connId) Remove node on disconnect
get(nodeId) Retrieve a node session by ID
listConnected() Return all currently connected node sessions
invoke(params) Send a command to a node and await the result
sendEvent(nodeId, event, payload) Push an event to a specific node
handleInvokeResult(params) Resolve a pending invocation promise with the node's result
Session Data

Each NodeSession tracks: connection ID, WebSocket handle, node identity (nodeId, deviceId), declared capabilities/commands/permissions, client metadata (platform, version), connection timestamp, and last activity time.

8. Node Invocation Flow

8.1 Normal Flow (Node Online)

  1. An operator sends a node.invoke request to the gateway, specifying the target nodeId and command.
  2. The gateway looks up the node in NodeRegistry and sends a node.invoke.request event to the target node.
  3. The node processes the command locally (camera snap, screen capture, location fetch, etc.).
  4. The node sends a node.invoke.result request back to the gateway.
  5. The gateway resolves the pending promise and returns the result to the operator.

8.2 Offline Flow (Node Disconnected + APNS Wake)

  1. Gateway detects the target node is offline.
  2. Gateway calls maybeWakeNodeWithApns(nodeId) to send a background push notification via APNS.
  3. APNS delivers the push; the node wakes and reconnects.
  4. Gateway waits 3–12 seconds for reconnection (waitForNodeReconnect).
  5. If reconnected, the gateway retries the invocation as in the normal flow.
  6. If the node remains offline, the gateway either returns an error or queues the work as pending (see Section 9).

8.3 Invocation Sanitization

Security Gate

Invocation parameters are validated and sanitized before dispatch (src/gateway/node-invoke-sanitize.ts). Only allowlisted commands (declared by the node at connect time) can be invoked. Parameters must conform to expected schemas. Sensitive data is not forwarded unnecessarily.

9. Pending Work Queue

Handles the case where a node is backgrounded (common on iOS/Android) and cannot receive real-time WebSocket messages.

Property Value
Max actions per node 64
Action TTL 10 minutes
Deduplication Via idempotencyKey

9.1 Action Schema

type PendingNodeAction = {
  id: string;              // Unique action ID
  nodeId: string;          // Target node
  command: string;         // Command to execute
  paramsJSON?: string;     // Serialized parameters
  idempotencyKey: string;  // Prevents duplicate processing
  enqueuedAtMs: number;    // Enqueue timestamp (epoch ms)
};

9.2 Work Types

Type Description
status.request Request current node status
location.request Request current device location

9.3 Lifecycle

1 Enqueue
Gateway queues work for offline node
2 Wake
APNS notification nudges node to foreground
3 Pull
Node reconnects and calls node.pending.pull
4 Execute
Node processes each action locally
5 Ack
Node calls node.pending.ack; actions removed

Expired actions (older than TTL) are silently discarded.

Source: src/gateway/node-pending-work.ts

10. Event Broadcasting

The gateway broadcasts events to all connected clients as state changes occur.

Event Description Recipients
connect.challenge Authentication challenge on new connection Connecting client

node.event Arbitrary node-originated event Operators

device.pair.requested New device pairing request Operators (pairing scope)

10.1 Sequence Numbers & Gap Detection

Gap Detection

Events carry optional seq (monotonically increasing) and stateVersion fields. Clients use these to detect missed events (gaps in seq) and request state resync when domain-specific versions (presence, health) are stale.

11. Client-Side Request/Response Pattern

The GatewayClient class implements the client half of the protocol.

11.1 Sending a Request

async request<T>(method: string, params: object, opts?: RequestOpts): Promise<T> {
  const id = uuid();
  const frame: RequestFrame = { type: "req", id, method, params };
  ws.send(JSON.stringify(frame));

  // Register a pending promise with a timeout (default 30s)
  return new Promise((resolve, reject) => {
    pending.set(id, { resolve, reject, timeout: setTimeout(...) });
  });
}

11.2 Receiving a Response

if (frame.type === "res") {
  const entry = pending.get(frame.id);
  if (entry) {
    clearTimeout(entry.timeout);
    pending.delete(frame.id);
    if (frame.ok) {
      entry.resolve(frame.payload);
    } else {
      entry.reject(new GatewayClientRequestError(frame.error));
    }
  }
}

11.3 Timeout Handling

If no response arrives within the timeout window (default 30 seconds), the pending promise is rejected with a timeout error. The client does not automatically retry.

Source: src/gateway/client.ts, src/cli/gateway-rpc.ts

12.2 Common Error Scenarios

Scenario Behavior
Protocol version mismatch Gateway rejects during handshake
Invalid signature Gateway rejects connect request
Node offline, APNS wake fails Error returned to operator (or work queued)
Command not in node allowlist Rejected at sanitization before dispatch
Request timeout (30s default) Client-side promise rejection
WebSocket close during invocation In-flight invocations rejected with disconnect error
Payload exceeds max size WebSocket frame rejected by transport

13. Security Model

13.1 Transport Security

  • Loopback (127.0.0.1) binding prevents remote access by default.
  • Remote deployments use wss:// (TLS) for encryption in transit.

13.2 Authentication

  • Challenge–response handshake proves device key possession.
  • Device tokens are issued by the gateway for streamlined reconnections.
  • Tokens are scoped to a specific device identity.

13.3 Authorization

  • Nodes are restricted to their declared caps, commands, and permissions.
  • Operators are restricted by their granted scopes.
  • Invocation parameters are sanitized before forwarding to nodes.

13.4 Trust Boundaries

Trust Architecture
  • The gateway is the trust anchor. Nodes and operators authenticate to it.
  • Nodes cannot invoke commands on other nodes directly — all routing passes through the gateway.
  • The gateway validates every RPC call against the caller's role and permissions before processing.

15. Summary

Protocol at a Glance
  • Three frame types (req, res, event) covering all communication patterns.
  • Challenge-based authentication using device keypairs for identity verification.
  • Role-based authorization separating operators (control plane) from nodes (capability hosts).
  • Bidirectional invocation allowing operators to execute commands on remote nodes through the gateway.
  • APNS-based wake for mobile nodes that are backgrounded or disconnected.
  • Pending work queue with TTL and idempotency for deferred command delivery.
  • Sequence-numbered events with domain-specific version counters for gap detection and state resync.
  • Strict sanitization of invocation parameters against node-declared command allowlists.

The protocol is designed for a hub-and-spoke topology where the gateway mediates all communication, enforces security policies, and manages node lifecycle — including wake, reconnection, and work queuing for intermittently connected mobile devices.
