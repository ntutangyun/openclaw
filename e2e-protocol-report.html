End-to-End Agent Task Execution Protocol Report

Comprehensive communication analysis · Operator → Gateway → Node → Cloud LLM · March 2026

Scenario

An operator (human user at a CLI/Web UI) asks an AI agent to search for, download, organize, and generate a report on IEEE Wi-Fi standards (802.11 family). The gateway orchestrates the task. A node (laptop device) executes file downloads and local filesystem operations. The agent’s reasoning is powered by a cloud LLM API (e.g., Anthropic Claude API). This report details every network communication, protocol, and data exchange across all four components.

1. System Architecture & Components

Figure 1 — Four-component architecture: Operator, Gateway, Node (laptop), Cloud LLM API, plus external Internet resources
Component Role Location Description
Operator Human user Local machine (CLI/Web/Desktop) Issues task instructions, receives progress updates and final results. Connects to gateway as role: operator.
Gateway Control plane & orchestrator Local machine or remote server Central hub that manages sessions, routes tool invocations to nodes, communicates with the Cloud LLM API for agent reasoning, and relays events to operators.
Node (Laptop) Capability host User’s laptop Executes file system operations (download, mkdir, write), runs shell commands, provides web browsing/fetching capabilities. Connects to gateway as role: node.
Cloud LLM API AI reasoning engine Remote cloud (e.g., api.anthropic.com) Provides the language model that powers the agent’s planning, reasoning, and text generation. Accessed via HTTPS REST API.
Internet (IEEE/Web) External data source Remote servers IEEE Xplore, standards.ieee.org, search engines. Accessed by the node via HTTPS to search and download standards documents.

2. Protocol Summary

Communication Link Transport Application Protocol Serialization Authentication Encryption
Operator ↔ Gateway TCP → WebSocket (RFC 6455) OpenClaw JSON-RPC (Protocol v3) JSON (text frames) Challenge-response + token TLS 1.3 (wss://) or plaintext for loopback
Node ↔ Gateway TCP → WebSocket (RFC 6455) OpenClaw JSON-RPC (Protocol v3) JSON (text frames) Device keypair + challenge-response TLS 1.3 (wss://) or plaintext for loopback
Gateway → Cloud LLM API TCP → HTTPS REST API (Anthropic Messages API / OpenAI-compatible) JSON API key (x-api-key / Authorization: Bearer) TLS 1.2/1.3
Node → Internet (IEEE/Web) TCP → HTTPS HTTP/1.1 or HTTP/2 HTML, PDF, JSON (varies) None (public) or session cookies TLS 1.2/1.3
Protocol Stack (per link)
  • Operator/Node ↔ Gateway: IP → TCP → TLS (optional) → HTTP/1.1 Upgrade → WebSocket → JSON-RPC frames
  • Gateway → Cloud LLM: IP → TCP → TLS 1.2+ → HTTP/1.1 or HTTP/2 → REST JSON + SSE (streaming)
  • Node → IEEE/Web: DNS resolution → IP → TCP → TLS 1.2+ → HTTP/1.1 or HTTP/2 → HTML/PDF/JSON content

3.4 Node ↔ Internet (IEEE/Web) HTTPS

When the agent instructs the node to fetch web content or download files, the node opens HTTPS connections to external servers. These are standard HTTP requests initiated by the node’s tool execution runtime.

Typical HTTPS Request to IEEE Xplore

GET /document/10376084 HTTP/2
Host: ieeexplore.ieee.org
User-Agent: OpenClaw-Node/2026.3.17
Accept: text/html,application/xhtml+xml,application/pdf
Accept-Encoding: gzip, br
Connection: keep-alive

PDF Download Request

GET /stampPDF/getPDF.jsp?arnumber=10376084 HTTP/2
Host: ieeexplore.ieee.org
Accept: application/pdf
Cookie: (session cookies if authenticated)
DNS Resolution

Before any HTTPS connection, the node’s OS resolver performs DNS lookups. For ieeexplore.ieee.org, this involves:

  1. Local DNS cache check (OS-level)
  2. Recursive DNS query (UDP port 53) to configured resolver (e.g., router, 8.8.8.8, or 1.1.1.1)
  3. A/AAAA record response with the server’s IP address
  4. TCP connection to resolved IP on port 443
  5. TLS 1.2/1.3 handshake with SNI (ieeexplore.ieee.org)

4. End-to-End Task Flow Overview

The complete task involves an agentic loop where the gateway repeatedly consults the Cloud LLM, dispatches tool calls to the node, feeds results back to the LLM, and streams progress to the operator. Below is the high-level phase structure:

1 Submit
Operator sends task to gateway
2 Plan
Gateway queries LLM for task plan
3 Search
Node executes web searches
4 Download
Node downloads IEEE PDFs
5 Organize
Node creates directory structure
6 Report
LLM generates report, node writes it
7 Deliver
Gateway sends result to operator

Step 2b: LLM streams response with tool calls

The LLM responds via SSE (Server-Sent Events). Each SSE event arrives as a separate chunk over the persistent HTTPS connection. The gateway parses each event incrementally. 

// The LLM's first turn output (assembled from SSE deltas):
{
  "id": "msg_01ABC",
  "type": "message",
  "role": "assistant",
  "content": [
    {
      "type": "text",
      "text": "I'll search for IEEE 802.11 Wi-Fi standards and organize them for you. Let me start by searching for information about each standard revision."
    },
    {
      "type": "tool_use",
      "id": "toolu_search_01",
      "name": "web_search",
      "input": {
        "query": "IEEE 802.11 Wi-Fi standards complete list 802.11a b g n ac ax be specifications"
      }
    }
  ],
  "stop_reason": "tool_use",
  "usage": { "input_tokens": 1847, "output_tokens": 156 }
}
SSE Protocol Details

The SSE stream uses the text/event-stream MIME type (W3C Server-Sent Events specification). Each event follows the format: 

event: <event-type>\ndata: <json-payload>\n\n

The gateway maintains a buffer and reassembles the full message from incremental content_block_delta events. For tool use, the input_json_delta events are concatenated and JSON-parsed once content_block_stop is received.

HTTP connection: The HTTPS connection remains open for the duration of the SSE stream. HTTP/2 multiplexing may allow multiple concurrent streams over a single TCP connection. The TCP connection can be kept alive via HTTP Keep-Alive for subsequent LLM turns in the same agent loop.

TLS Certificate Verification

During each TLS handshake with IEEE servers, the node verifies:

  • Certificate chain up to a trusted root CA
  • Server name matches the certificate’s Subject Alternative Name (SAN)
  • Certificate expiration (not expired, not yet valid)
  • Revocation status via OCSP stapling or CRL (optional)

The cipher suite negotiated is typically TLS_AES_256_GCM_SHA384 or TLS_CHACHA20_POLY1305_SHA256 for TLS 1.3.

12. Streaming & Progress Updates

Throughout the entire agentic loop, the gateway maintains real-time communication with the operator via WebSocket event frames.

12.1 Event Types Sent to Operator

Event Trigger Payload
agent.progress Agent starts a new phase/tool { turn, status, tool, detail, progress }
agent.text LLM produces text output (streamed) { turn, text, delta }
agent.tool_start Tool invocation dispatched to node { turn, toolName, args, invocationId }
agent.tool_complete Tool invocation returned from node { turn, toolName, result, durationMs }
agent.error Tool or LLM call fails { turn, error, retryable }
agent.complete Agent finishes all turns { status, summary, artifacts, usage }

12.2 Streaming Architecture

Three-Tier Streaming Pipeline
  1. Cloud LLM → Gateway (SSE): The LLM streams token-by-token via Server-Sent Events over HTTPS. Each content_block_delta event contains a small text or JSON fragment.
  2. Gateway processing: The gateway reassembles SSE deltas, detects tool_use blocks, and decides when to forward text to the operator vs. when to dispatch tool invocations to the node.
  3. Gateway → Operator (WebSocket events): The gateway pushes real-time agent.text events containing LLM text deltas, plus agent.progress / agent.tool_start / agent.tool_complete events for tool activity.

12.3 Keepalive

During long operations (e.g., downloading large files), the WebSocket connections are kept alive via:

  • WebSocket ping/pong frames (RFC 6455 §5.5.2/5.5.3) sent at tickIntervalMs (30s).
  • TCP keepalive at the OS level (typically 60s for loopback, configurable for remote).
  • LLM connection: HTTP Keep-Alive or HTTP/2 stream idle timeout (typically 60–120s). The gateway may need to re-establish the TLS+HTTP connection if the gap between LLM turns exceeds the server’s idle timeout.

13. Error Handling & Retries

13.1 Error Categories by Link

Link Error Type Protocol Indicator Recovery Strategy
Operator ↔ Gateway WebSocket disconnect TCP RST / WS close frame (1006) Auto-reconnect with exponential backoff; agent continues; operator catches up via state sync
Node ↔ Gateway Node offline during invocation WS close / no response within timeout Invocation queued in pending work queue; retried when node reconnects
Gateway → Cloud LLM Rate limit (429) HTTP 429 + retry-after header Gateway retries after specified delay; operator sees agent.progress “rate limited”
Gateway → Cloud LLM Server error (500/502/503) HTTP 5xx Exponential backoff retry (up to 3 attempts)
Gateway → Cloud LLM Context too long (400) HTTP 400 + error.type: "invalid_request_error" Gateway truncates/summarizes conversation history and retries
Node → Internet Download fails (404, timeout) HTTP 404 / TCP timeout Node returns error to gateway; LLM decides whether to retry, skip, or try alternative URL
Node → Internet TLS certificate error TLS alert (unknown_ca, expired) Node returns TLS error; LLM may suggest alternative source
Node → Internet DNS resolution failure DNS NXDOMAIN / SERVFAIL Node returns DNS error; LLM may suggest alternative hostname or retry

14.3 Authorization & Capability Gating

Tool Authorization Chain

Before the gateway dispatches a tool invocation to a node, it checks:

  1. Operator scopes: Does the operator’s session include operator.write?
  2. Node capabilities: Does the target node declare the required caps and commands?
  3. Node permissions: Is the specific permission (e.g., fs.write) enabled?
  4. Approval flow: For sensitive operations, the gateway may send an approval.request event to the operator and wait for approval.respond before dispatching.

Performance Insight

The overwhelming bottleneck is Cloud LLM inference latency, accounting for approximately 70% of total wall-clock time. Network latency between local components (operator, gateway, node) is negligible by comparison. The second largest contributor is external HTTPS downloads from IEEE servers.

HTTP/2 multiplexing and TCP connection reuse help reduce overhead for repeated calls to the same Cloud LLM endpoint. The gateway maintains a connection pool for this purpose.

17. Summary

Key Takeaways
  1. Four distinct protocols are involved: WebSocket JSON-RPC (operator/node ↔ gateway), HTTPS REST + SSE (gateway ↔ cloud LLM), HTTPS (node ↔ internet), and DNS (node → resolvers).
  2. The gateway is the central orchestrator. It never directly accesses the internet for content; all file operations happen on the node. The gateway’s role is to shuttle tool calls between the LLM’s reasoning and the node’s execution capabilities.
  3. The agentic loop is an iterative cycle: Gateway sends context to LLM → LLM responds with tool calls → Gateway dispatches to node → Node executes and returns results → Gateway feeds results back to LLM → repeat until the LLM returns stop_reason: "end_turn".
  4. Approximately 81 distinct network exchanges occur in this scenario across 7 LLM turns and 17 tool invocations.
  5. Cloud LLM inference is the dominant latency, accounting for ~70% of total wall-clock time. Local WebSocket communication adds minimal overhead.
  6. Security is layered: TLS encrypts all cross-boundary communication, device keypairs authenticate nodes, API keys authenticate the LLM, and capability gating ensures nodes only execute authorized operations.
  7. Error resilience is built into every link: WebSocket reconnection for operator/node, retry with backoff for LLM rate limits, and error-as-tool-result for failed tool executions (allowing the LLM to adapt its strategy).
